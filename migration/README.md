# Миграция HOME-VPN на несколько серверов

Целевая схема:

- **RU-1** — главная 3x-ui, центральная база, сайт и API.
- **PL-2** — дополнительная 3x-ui-нода и Telegram-бот. Бот обращается только к API RU-1.
- **FI-3** — дополнительная 3x-ui-нода с существующими клиентами и доменом подписки.
- **NODE-4** — дополнительная нода с существующими клиентами и доменом подписки. Страну нужно уточнить: в исходном описании обе последние ноды названы финскими.

Переменные RU-сайта после переноса:

```ini
PUBLIC_URL=https://vpn.my.domain.ru
XUI_URL=https://127.0.0.1:2053/your-panel-path
XUI_TOKEN=...
XUI_INBOUND_IDS=1,2,3,4
PRIMARY_NODE_NAME=RU-1 — основная нода
PRIMARY_NODE_FLAG=🇷🇺
```

Переменные бота на PL-2:

```ini
SHOP_API_URL=https://vpn.my.domain.ru
PUBLIC_BASE_URL=https://vpn.my.domain.ru
SHOP_API_SECRET=...
ADMIN_PANEL_URL=https://vpn.my.domain.ru/private-admin-path
```

На PL-2 не нужна копия базы сайта: заказы, Telegram-привязки, тикеты, уведомления и соответствие клиентов хранятся централизованно на RU-1. Локально бот хранит только курсор уже обработанных событий.

Сайт и бот больше не предполагают фиксированное число стран: статусы и подключения берутся из главной 3x-ui. Ссылка HOME-VPN агрегирует подключения, которые возвращает главная панель.

## Безопасный порядок

1. Сделать снимок/резервную копию базы каждой 3x-ui и конфигурации используемого веб-сервера, если он есть.
2. Заполнить `nodes.json` по примеру `nodes.example.json`. Секреты хранить только в переменных окружения.
3. Выполнить сухую инвентаризацию:

   ```bash
   python3 migrate_existing_clients.py nodes.json --report before-migration.json
   ```

4. Разобрать все строки `conflict`. Скрипт никогда не перезаписывает клиента с тем же email, но другим UUID или `subId`.
5. Импортировать отсутствующих клиентов с исходными UUID и `subId`:

   ```bash
   python3 migrate_existing_clients.py nodes.json --report applied.json \
     --apply --confirm IMPORT_EXISTING_CLIENTS
   ```

6. В главной RU-панели добавить PL/FI/NODE-4 как управляемые ноды и проверить, что синхронизация не создаёт новые UUID поверх импортированных.
7. Проверить старые домены подписок. Их маршруты существующего веб-сервера нельзя удалять или перекрывать заглушкой. Менять можно только точную главную страницу `/`, не затрагивая URL подписок.
8. Проверить тестового клиента: старый URL, ссылка с сайта, QR, все страны в HAPP, продление, изменение числа устройств и уведомление Telegram.
9. Только после успешной проверки переключать DNS/боевые домены.

`preferred_legacy_link: true` регистрирует старый доменный URL как ссылку, которую сайт и бот продолжают выдавать данному клиенту. Используйте этот режим только если URL уже возвращает актуальный общий набор узлов либо существующий веб-сервер позднее направляет его на центральную подписку.

После подключения нод метод главной панели `/panel/api/clients/links/<login>` должен возвращать подключения всех стран. Именно из него центральный endpoint `/client-sub/...` строит единую подписку для HAPP; отдельные ссылки пользователю не нужны.

Скрипт не удаляет клиентов, не меняет удалённые панели и не записывает токены в отчёт. Применение требует отдельного флага и контрольной фразы.
