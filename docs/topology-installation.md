# Установка HOME-VPN по одной из трёх архитектур

Сценарий `scripts/install-home-vpn-topology.py` запускается с рабочей станции,
которая имеет root SSH-доступ ко всем VPS. GitHub при этом не
используется: на VPS передаётся снимок текущего локального каталога проекта.

Исключение — готовый однонодовый мастер `install-single-node.sh`: он запускается
непосредственно на чистой VPS, создаёт mode 3 plan с целью `local` и не требует
SSH-подключения сервера к самому себе. Его использование описано в
[основной инструкции](installation.md#быстрая-интерактивная-установка-на-vps).

## Поддерживаемые режимы

| Режим | Главная нода | Зарубежные ноды | Путь VPN-трафика |
|---|---|---|---|
| 1 — прямой | сайт, Telegram-бот и все HOME-VPN web-панели на RU VPS | 11 подключений 3x-ui на каждой | пользователь → зарубежная нода → интернет |
| 2 — каскад | сайт, Telegram-бот, web-панели и VPN-вход на RU VPS | 11 подключений 3x-ui на каждой | пользователь → RU VPS → зарубежная нода → интернет |
| 3 — одиночный | единственная иностранная VPS выполняет управляющую роль: сайт, бот и web-панели | тот же сервер: 11 подключений | пользователь → зарубежный сервер → интернет |

В режимах 1 и 2 на каждой дополнительной ноде устанавливается простой
сайт-заглушка на порту `8181`. Она не содержит кабинета и ведёт пользователя на
главный сайт. Панели 3x-ui остаются административными и не публикуются как
пользовательский интерфейс.

На главной управляющей ноде заглушка запрещена: сценарий устанавливает полный
сайт HOME-VPN и при повторном развёртывании удаляет оставшуюся от прежней роли
службу `home-vpn-placeholder`. В одиночном режиме 3 сайт HOME-VPN также работает
на единственной иностранной VPS, а заглушка не устанавливается.

Сайт, кабинет пользователя, HOME-VPN admin и панель управления ботом физически
работают только на управляющей VPS: центральной в modes 1/2 или единственной
иностранной в mode 3. На дополнительных зарубежных VPS остаётся технический API
3x-ui, потому что без него управляющая панель не сможет создавать подключения.
Сценарий записывает его адрес из защищённой межсерверной сети. На внешнем
firewall разрешите порт API 3x-ui только с адреса центральной VPS; не публикуйте
панель зарубежной ноды в Интернет.

Под «11 подключениями» понимаются десять базовых VPN-подключений и
одно MTProto. Если на ноде уже существует ровно такая схема, мастер сохраняет
её. Частично настроенную или отличающуюся схему он не удаляет автоматически и
останавливается, чтобы не повредить работающий сервер.

## Требования до запуска

- VPS уже созданы, запущены и имеют стабильные адреса в защищённой межсерверной сети;
- с рабочей станции работает `ssh root@<vps> id -u`, команда возвращает `0`;
- DNS, внешние NAT/firewall и сертификаты подготовлены отдельно;
- API 3x-ui зарубежных узлов доступен центральной VPS по защищённой сети и закрыт для остальных источников;
- если API использует HTTPS, `api_host` должен быть DNS-именем из сертификата и разрешаться на защищённый адрес ноды;
- для режима 2 каждому зарубежному узлу выделен уникальный входной IP на центральной VPS;
- секреты 3x-ui, Telegram и сайта не внесены в JSON-план и Git.
- HTTPS URL внешнего установщика протоколов и его SHA-256 получены из доверенного источника.

Для новой одиночной VPS используйте сначала полную последовательность подготовки
DNS, SSH, TLS и firewall из [основной инструкции](installation.md). Topology
installer не создаёт DNS-записи, не получает сертификат и запускает KIT с
`--no-ufw`, поэтому эти шаги нельзя пропускать.

Уникальные IP в режиме 2 обязательны: все ноды используют одинаковый набор
портов, поэтому только по порту центральная VPS не сможет определить конечную ноду. Клиентские
ссылки должны указывать домен или IP соответствующего ingress.

## Интерактивный мастер

Сначала запустите только планирование:

```bash
python3 scripts/install-home-vpn-topology.py \
  --write-plan topology.local.json
```

Мастер спросит режим, SSH-адреса VPS, сетевые адреса, домены, SNI и пути к сертификатам.
Файл плана не содержит паролей и токенов, но локальные планы всё равно не следует
публиковать. Проверьте показанную схему и затем примените её:

```bash
python3 scripts/install-home-vpn-topology.py \
  --config topology.local.json \
  --apply \
  --confirm 'INSTALL HOME VPN TOPOLOGY'
```

Для начала можно скопировать [пример конфигурации](../config/topology.example.json).
В примере URL и SHA-256 являются заглушками: перед `--apply` замените их на реальные и проверенные значения.
Без `--apply` сценарий всегда завершает работу в режиме dry-run и ничего не
меняет.

## Что делает сценарий

1. Проверяет root SSH-доступ ко всем VPS.
2. Загружает указанный установщик набора протоколов и проверяет SHA-256.
3. Устанавливает 11 подключений на каждой VPN-ноде или проверяет совместимость
   уже установленной схемы.
4. Включает штатный локальный backup KIT с проверкой SQLite и SHA-256.
5. Получает фактические inbound ID и API-токены из каждой ноды.
6. Создаёт или обновляет сайт с конфигурацией нескольких нод.
7. Создаёт служебного VLESS/XHTTP-клиента на каждой зарубежной ноде.
8. На управляющей VPS запускает закрытый loopback HTTP-прокси с `leastPing` и health-check всех XHTTP-выходов. Недоступные ноды исключаются, а при отказе всего пула прямой выход запрещён.
9. Устанавливает Telegram-бот и loopback-only web-панель на управляющей VPS; панель публикуется через закрытый TLS path сайта, и только Telegram API идёт через egress-прокси.
10. Удаляет старую заглушку с управляющей ноды и устанавливает заглушки только на дополнительных нодах в режимах 1 и 2.
11. В mode 3 идемпотентно направляет catch-all XHTTP fallback на HOME-VPN `127.0.0.1:8080`.
12. В режиме 2 создаёт проверяемую `nftables`-таблицу DNAT/SNAT; при выходе из cascade удаляет только проектную таблицу и восстанавливает прежний `ip_forward`.
13. Проверяет обязательные systemd-сервисы и публичный `/health`.

Пароли и токены мастер запрашивает только непосредственно перед применением.
Они передаются через stdin и временные файлы `0600`, которые удаляются после
установки. В аргументы команд и JSON-план секреты не попадают.

Балансировщик принимает соединения только на `127.0.0.1`, разрешает только
`api.telegram.org` и выбирает health-aware VLESS/XHTTP-выход через `leastPing`. Observatory
исключает недоступные ноды. Если не работает ни один иностранный выход,
соединение блокируется: прямого обхода через публичный адрес RU VPS нет.

Новые пользовательские подписки распределяет управляющий сайт: учитываются
доступность, число активных клиентов, незавершённые назначения, вес,
`maintenance` и `accept_new`. При полном отказе возвращается 503, и заказ не
создаётся. После
выдачи подписка закрепляется за выбранной нодой, поэтому уже работающий клиент
не переключается самопроизвольно.

## Проверка после установки

```bash
# Управляющая VPS сайта (в mode 3 — единственная иностранная VPS)
systemctl is-active vpn-shop
curl -fsS https://vpn.my.domain.ru/health

# Каждая VPN-нода
systemctl is-active x-ui nginx kit-sub home-vpn-kit-backup.timer
sudo systemctl start home-vpn-kit-backup.service
sudo systemctl status home-vpn-kit-backup.service

# RU VPS: Telegram-бот, панель и балансировщик
systemctl is-active vpn-bot vpn-bot-admin home-vpn-bot-egress
ss -lnt | grep 127.0.0.1:8090
! ss -lnt | grep 0.0.0.0:8090
curl -x http://127.0.0.1:18080 -fsS https://api.telegram.org/ >/dev/null
```

Для режима 2 дополнительно:

```bash
systemctl is-active home-vpn-cascade.service
nft -c -f /etc/home-vpn/cascade.nft
nft list table ip home_vpn_cascade
sysctl net.ipv4.ip_forward
```

В mode 1 и mode 3 таблица `home_vpn_cascade`, unit, `cascade.nft` и sysctl
drop-in должны отсутствовать. Полный read-only smoke-test:

```bash
python3 scripts/smoke-home-vpn-topology.py --config topology.local.json
```

Проверяйте VPN с внешней сети, а не только из LAN. Для каждой ноды создайте
отдельного тестового клиента, откройте подписку, проверьте подключение и внешний
IP. Затем удалите тестового клиента через сайт.

## Повторный запуск и безопасное изменение режима

Сценарий рассчитан на повторный запуск: существующие базы сайта и бота не
пересоздаются, конфигурация и исполняемые файлы обновляются. Однако перенос уже
выданных клиентов между нодами не выполняется автоматически. Сначала сохраните
KIT backup и проверьте восстановление по [инструкции](backup-and-restore.md).

Для перехода между прямым и каскадным режимом обновите `mode`,
`ingress_address` и `public_host` в локальном плане, выполните dry-run и только
после проверки примените план. Переход меняет адреса в новых клиентских ссылках;
DNS/NAT/firewall остаются ответственностью администратора.

## Ограничения

- сценарий не создаёт VPS, DNS-записи, публичные IP и правила внешнего firewall;
- локальный KIT backup не защищает от потери VPS; off-site-копию
  нужно делать средствами провайдера или NAS с правами без удаления со стороны ноды;
- автоматического отката межсерверной установки нет, поэтому перед изменением
  работающей среды нужен проверенный backup;
- сертификаты и закрытые ключи задаются путями на соответствующей VPS.
